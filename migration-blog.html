01 / CONTEXT

为什么不是“换一台显卡再跑一次”

具身智能仓库通常同时依赖物理引擎、渲染后端、机器人资产、数据格式、训练框架和策略执行器。NVIDIA 环境中一次成功，不能推出 AMD 环境中整条链路成立。尤其是闭环任务：模型每一步都要读到正确的图像和状态，再把正确尺度的动作交给模拟器；只要其中一层偏移，loss 仍可能下降，视频也仍然播放，但机器人已经无法完成任务。

因此我们的迁移目标不是“导入不报错”，而是完成下面这个可追踪闭环：

环境与设备→场景与资产→专家数据→训练与 checkpoint→推理 bridge→固定评估
迁移的核心判断

如果只完成了前两步，应称为“仿真运行验证”；如果完成了训练，只能称为“训练链路验证”；只有固定任务、固定 seed、完整分母、成功/失败视频和结果 JSON 同时存在，才可以称为“闭环结果”。

02 / ACCEPTANCE

六层验收：每一层都要有自己的证据

我们把迁移拆成六个门禁。每个门禁有不同的失败含义，也有不同的修复方式。这样可以避免把一个无窗口 smoke、一次能导入或一条看起来“动起来了”的视频误报成模型成功。

01

环境

记录 ROCm、HIP、Python、PyTorch/JAX、模拟器和关键插件版本。验证 GPU backend，而不是只看 Python import。

02

仿真

官方场景完成 reset、step、render，能在无窗口服务器上保存 MP4；告警和物理失败分开。

03

数据

审计 observation/action 维度、时间顺序、episode 边界、终止 padding 和 normalization stats。

04

训练

官方入口能启动，日志可读，checkpoint 可校验，断点续训不会悄悄改变 output_dir 或配置。

05

推理

推理使用与训练匹配的权重、tokenizer、stats、相机映射、action chunk 和执行节奏。

06

评估

固定任务、seed、进程拓扑和分母；每条结果绑定 JSON、视频和 SHA，并区分正式、诊断、展示。

03 / CASE STUDY

DISCOVERSE：从“能启动”到四个高清任务

DISCOVERSE 是我们迁移工作中最完整的一条线。它同时涉及 MuJoCo 任务、AIRBOT/MMK2 机器人、专家轨迹、ACT/DP/PPO/RDT 入口、无窗口渲染、MP4 输出以及 ROS2、LiDAR、3DGS 等外围能力。迁移时最容易犯的错误，是把核心 demo 通过等同于所有真实硬件都已可用；我们把两者明确拆开。

3.1 迁移中最棘手的 IK 问题

block_bridge_place 的官方 79 阶段专家路径曾暴露出 IK 不可达和碰倒支撑的组合问题。增加支撑质量、降低末层高度都没有得到稳定通过。正确处理不是把评估分母改掉，也不是把失败轨迹替换成一条“更容易”的轨迹，而是把问题单独标为专家路径/任务设计问题；另一条严格的专家 suffix 回放链路最终达到 31/31，并保留原始失败证据。

3.2 无窗口渲染不是“没有画面”

服务器没有桌面时，窗口渲染不可用，但任务本身仍可运行。我们将 MuJoCo offscreen、OSMesa 或平台对应的 headless 后端作为正式输出，并把 RGB 帧编码为 MP4。渲染告警、画面分辨率和物理成功必须分别记录：有视频不代表成功，有 denoiser 告警也不必然代表物理失败。

3.3 高清多视角展示

为了让学习者看到真实任务，而不是只看到一张低分辨率视窗，我们补做了四个 MMK2 官方任务的三机位原生视频：box pick、drawer open、cabinet door open、coffee cup to plate。每个任务均为严格 1/1 成功，原生视频为 1920×1080；网站只展示相对路径和 SHA 清单，展示视频不改变训练数据和正式分母。

04 / CASE STUDY

RoboCasa365：资产、协议和视觉质量必须同时对齐

RoboCasa365 的难点不只在策略。官方资产包、任务注册、MuJoCo 渲染、Pi0.5 的 JAX 推理、GR00T 推理、视频保存和 16×50 正式评估都必须保持一致。最初我们还遇到过结果目录层级较深，简单的 stats glob 找不到 timestamp 子目录，最终生成了看似完整但实际是 0/0 的汇总；修复后改为持久化归档和正确的递归结果扫描。

4.1 完整资产先验收，策略后验收

官方资产包下载后先做文件大小、校验值、解压数量和 reset/render smoke。资产包完整只说明场景可复现，不说明随机策略或模型成功。我们把“资产可用”“场景可视化”和“策略成功率”分成三行写入记录，避免把 0/1 的随机运行验证误读成模型成绩。

4.2 正式评估和宣传视频不是同一件事

正式评估的优先级是固定任务、固定 seed、完整分母和可核对 JSON；宣传视频的优先级是清晰、连续、多视角和可读性。两者可以共用模型，但不能互相替代。网站中的长程四视角视频标记为 showcase，正式 16×50 结果仍然保持原协议。

05 / CASE STUDY

ROCm JAX 与 Pi0.5：为什么“支持 JAX”不等于每个策略都能直接跑

AMD 官方已经提供 ROCm JAX 路线。真正的迁移工作是让 Python、ROCm、JAX、jaxlib、ROCm plugin、PJRT 和模型代码处于互相匹配的版本集合，而不是单独把某个 pip 包升级。我们按 AMD 官方路线建立了隔离的 JAX 0.10.0 环境，GPU backend 识别为 rocm:0，gfx1151，64×64 矩阵计算通过。

官方 JAX 预检与策略闭环是两个门禁

矩阵计算通过，只能说明基础运行时和一个算子可用；还要继续验证 checkpoint restore、tokenizer、normalization stats、视觉编码器、attention、相机输入、动作解码和环境闭环。我们在页面中把这两类结果分开，不把预检写成成功率。

5.1 旧环境为什么会失败

DexJoCo 旧环境是 ROCm 7.2.1/JAX 0.8.2：GPU 可见，但 GEMM 触发 hipGetFuncBySymbol。这不是“模型没有学会”，而是运行时或插件在目标 gfx 上无法完成算子调用。另一条 Pi0.5 路线还出现过 Gemma attention 的 64 KiB shared-memory 限制、MIOpen 卷积编译错误和 headless 视频依赖问题。

5.2 修复顺序

  1. 先固定官方 AMD JAX 版本组合并做 backend、矩阵、卷积和 attention 预检。
  2. 再恢复 Orbax 参数、tokenizer 和归一化统计，确认没有把参数树或 StepMetadata 当成普通字典。
  3. 对单个容易诊断的任务做真实闭环，保留 MP4 和 action trace。
  4. 最后按官方多任务协议评估，单任务成功只作为诊断，不替代多任务分母。

06 / POLICY STACK

策略模型迁移：训练能跑、推理能跑、任务成功是三件事

在 Every Embodied 线，我们保留了保护权重、Notebook 原生训练和严格评估之间的绑定关系。结果如下：SmolVLA 57/60，Pi0 12/14，ACT 当前重建 7/30。ACT 的低分不是迁移失败的证明，而是一个有价值的负例：loss、视频运动和接近物体都不能替代 strict physical success。

在 RoboWits W7900 线上，官方 16-D ACT 100k checkpoint 的高清评估也必须看完整任务结果。当前公开可引用的任务结果是：06_dominos 2/5，14_stack_cubes 0/5，19_stack_bowls 0/5，25_water_into_mug 0/5。它说明训练和 checkpoint 运行链路已经成立，但模型在这些任务上还没有达到可提交的稳定成功率。

为什么不只报告最好的一条视频？

最好视频适合演示，完整分母适合比较。我们会同时保留成功和失败案例，按 approach/contact/grasp/lift/transport/place/release 分析失败阶段；这样才能知道下一步是补数据、修 action bridge、改 chunk 执行，还是重新检查相机与归一化。

07 / DEBUGGING

迁移中反复出现的九类问题

01 · GPU 身份

为什么日志写 torch.cuda？

ROCm 仍复用 PyTorch 的 torch.cuda API。判断是否真的在 AMD 上运行，要同时记录 torch.version.hip、rocminfo、GPU 型号和实际显存占用。

02 · Headless 渲染

为什么有窗口告警但任务还能跑？

Vulkan、CUDA denoiser 或无 DISPLAY 警告可能只影响渲染路径。要单独验证 offscreen 图像、MP4 编码、物理状态和成功谓词。

03 · JAX 算子

为什么 GPU 可见仍然 GEMM 失败？

backend 可见只代表设备枚举完成；plugin、PJRT、MIOpen、attention 和特定 gfx kernel 仍可能失败。固定版本组合比盲目升级单包更重要。

04 · Action chunk

为什么动作看起来像对但抓不住？

检查 chunk 长度、重叠执行、temporal ensemble、absolute/relative qpos、夹爪编码和控制频率。单步输出正确不代表持续执行正确。

05 · Normalization

为什么同一模型换环境就漂？

必须绑定训练时的 stats、相机尺寸、颜色顺序、状态维度和动作尺度。stats 不匹配会让策略“有动作但没有物理意义”。

06 · 数据边界

为什么 teacher-forced 很好，闭环很差？

教师强制没有暴露累计误差。固定 seed 闭环失败后，保留 action trace，判断失败发生在接近、接触、抓取、抬升还是释放。

07 · 资产授权

为什么不能随便替换一个模型？

缺少官方 BlenderKit 或专属资产时，必须单独标记 blocked；替换资产会改变任务分布，也会破坏论文和官方分母。

08 · 评估拓扑

为什么同一 seed 第二次结果不一样？

冷启动、热复用、并行 worker、随机数初始化和视频保存路径都会影响结果。固定单进程拓扑和 seed，才能比较 checkpoint。

09 · 远端存储

为什么云端重启后任务消失？

PVC 通常保留数据，但 SSH 服务、系统包、动态端口和进程不会自动恢复。训练脚本、环境记录、checkpoint 同步和重连说明都要放在持久目录。

08 / REPRODUCTION

学习者如何从零复现

不要一开始就下载所有模型。先做小闭环，再扩展到长训和正式评估。下面的命令使用占位变量，避免把机器路径写死到教程中；具体仓库的脚本、Notebook 和公开权重应作为唯一入口。

export PROJECT_ROOT=/path/to/datawhale-eai-amd-physical-ai
export DATA_ROOT=/path/to/data

# 1. Verify the AMD runtime
python -c "import torch; print(torch.__version__, torch.version.hip, torch.cuda.is_available())"
rocminfo | head -n 30

# 2. Run an official reset/render smoke and save an MP4
python scripts/robocasa_amd_smoke.py --output results/smoke

# 3. Check the artifact before evaluation
sha256sum results/formal/eval_info.json
ffprobe -v error -select_streams v:0 \\
  -show_entries stream=width,height,r_frame_rate \\
  -of default=noprint_wrappers=1 results/formal/success.mp4

# 4. Only then run the fixed task/seed evaluation
python scripts/evaluate_official.py \\
  --checkpoint /path/to/checkpoint \\
  --seeds 0 1 2 3 4 \\
  --save-video --output results/formal

09 / PUBLICATION

公开什么，保留什么

成果站公开的是方法、版本组合、结果摘要、代表性视频、公开上游链接和 SHA。私有比赛仓库保留 AMD bridge、补丁、原始日志、受限资产、未发布权重和设备配置。这样既能让学习者复现公开链路，也不会把凭据、私有地址、未授权资产或敏感训练细节直接暴露。

  • 公开：迁移门禁、问题分类、修复原则、结果 JSON、代表视频、公开权重链接、上游仓库。
  • 不公开：token、SSH 私钥、云端端点、个人绝对路径、私有资产、未经授权的 BlenderKit 内容。
  • 不夸大：诊断成功、展示视频、专家回放和正式成功率永远分开标记。
  • 可复核：每个正式结果绑定任务集合、seed、分母、JSON、视频和 SHA256。
